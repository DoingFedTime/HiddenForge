# Publish any app as a `.onion`

hiddenforge is a sidecar. You keep your application exactly as it is, attach it to
one network, and hiddenforge gives it a Tor v3 address. There is no `.onion`
toolchain to install: the address generator ships in the image. The
`hiddenforge` CLI used below is one file, `scripts/hiddenforge` (Python 3.10 or
later, standard library only); put it on your PATH.

This document is the integration contract. Every command here is tested
(`tests/test_cli.py`, `tests/test_e2e_live.py`, `examples/demo`).

---

## 1. The minimal merge (3 commands)

```bash
# 1. Emit a compose fragment next to your compose file.
hiddenforge setup --backend web:80 --name myapp --out ./deploy
#    (--backend is YOUR service name and port; --name is the service/dir name)

# 2. Merge it and start. Do not edit the fragment.
docker compose -f compose.yml -f ./deploy/compose.service.yml up -d

# 3. Read the address once it is ready.
hiddenforge show --keys ./tor-keys --name myapp --json
```

`setup` writes four files and edits none of yours:

| File | What it is |
|---|---|
| `compose.service.yml` | the merge fragment: `tor` service, both networks, key volume, caps, hardening, env, healthcheck (Docker only -- see below) |
| `deploy.sh` | the same three steps as a script |
| `README.txt` | human summary of what was generated |
| `hiddenforge.json` | machine descriptor (name, env var, merge command, address command) |

Your app **must**:
- join the `tor-internal` network (`networks: [tor-internal]`),
- publish **no** ports (`ports:` must be absent),
- be reachable from the `tor` container by the service name you passed to
  `--backend`.

That is the entire contract. The shipped `examples/demo` is a working consumer.

### Multiple services, and Podman

`--service` is repeatable, so one command emits every onion you need:

```bash
hiddenforge setup \
  --service blog:80:blog:80 --service blog:443:blog:443 \
  --service tips:80:tips:8080 \
  --out ./deploy
```

This writes one `{NAME}_TOR_SERVICE_HOSTS` per service (mappings for the same
name are joined: `"80:blog:80,443:blog:443"`) and a `depends_on` for each real
backend service. Podman users add `--runtime podman`, which drops the
Docker-only `apparmor=` option, leaves out the healthcheck (rootless Podman 4.9
never restarts a container that has one when no systemd user session is
reachable, and restarting is how this container recovers), and has
`deploy.sh` use Docker Compose on the rootless Podman socket when the Compose
binary is installed (the only way every declared limit is applied), else
`podman-compose` with a warning about the limits it skips. It keeps all five
capabilities: setup cannot tell a rootless engine from a rootful one, and the
three-capability set of the shipped `podman-compose.yml` breaks a rootful first
boot. On rootless Podman you may drop `DAC_OVERRIDE` and `FOWNER` from the
fragment, as the shipped file does.

`setup` refuses to overwrite any of its four output files that already exist
unless `--force` is given, so a hand-tuned fragment is not clobbered by a re-run
(other files in the directory are left alone).

### Which compose file is which

| File | Role |
|---|---|
| `docker-compose.yml` | Docker quick start, in this repository |
| `podman-compose.yml` | Rootless Podman quick start, in this repository |
| `examples/demo/app.yml` | A demo backend with no Tor service, merged with a generated fragment. It shows the smallest consumer and is not a hardened production file |
| `compose.service.yml` | Generated by `setup` for your deployment. Not in this repository |
| `compose.yml` | In the examples on this page, your own base file with your application. Not in this repository |
| `tests/golden_setup/compose.service.yml` | The expected output of `setup`, compared by a test. Not deployable |

The two shipped files differ on purpose:

| Setting | `docker-compose.yml` | `podman-compose.yml` | Why |
|---|---|---|---|
| Tor `restart` | `unless-stopped` | `always` | After a reboot Podman's boot service starts only `always` containers |
| Tor capabilities | `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID`, `SETGID` | `CHOWN`, `SETUID`, `SETGID` | In rootless Podman container root already owns the key bind mount |
| Tor healthcheck | `healthcheck.py` every 60 s | none | Rootless Podman 4.9 never restarts a container that has one when no systemd user manager is reachable |
| Tor `apparmor` | `docker-default` | not set | Rootless Podman often cannot load `docker-default` and applies its own |
| `/var/lib/tor` tmpfs | `uid=100,gid=101,mode=0700` | no owner options | Those tmpfs options are Docker-specific; the entrypoint chowns the directory |
| Backend capabilities | adds `DAC_OVERRIDE` | adds `NET_BIND_SERVICE` instead | Rootless Podman cannot bind ports below 1024 without it |
| Backend `restart` | `unless-stopped` | `always` | Same boot-service reason as for Tor |
| Backend `apparmor` | `docker-default` | not set | Same as for Tor |
| Backend image name | `nginx:alpine@sha256:...` | `docker.io/library/nginx:alpine@sha256:...` | Podman wants the fully qualified name |
| Limits | applied by Docker | applied by Docker Compose on the Podman socket; `podman-compose` skips `memswap_limit`, and `pids_limit` before 1.1 | Run `hiddenforge doctor` to see what was applied |

Everything else is identical: `cap_drop: ALL`, `no-new-privileges`, the read-only
filesystem, the tmpfs mounts, memory and CPU limits, `pids_limit: 256`, `dns:
127.0.0.1`, `logging: driver: none`, and the two networks.

### What `--backend` produces

`--backend web:80 --name myapp` emits:

```yaml
environment:
  MYAPP_TOR_SERVICE_HOSTS: "80:web:80"
```

The native form is `{NAME}_TOR_SERVICE_HOSTS=onion_port:backend_host:backend_port[,...]`.
You can set it by hand instead of using `setup`; that is the same contract the
existing `docker-compose.yml` uses.

> **Backend hostnames are resolved at container start** and the IP written into
> the torrc. If the backend is recreated on a different IP, the supervisor sees
> the name move (two successful lookups in a row without the old IP, checked every
> 30 seconds) and exits so the restart policy brings the container back with a
> fresh lookup; the address is unchanged. Keep a restart policy on the service
> (the fragment sets `restart: unless-stopped`, or `always` for Podman). A backend that is merely down, or
> a DNS failure, never triggers this. A backend whose name does not resolve yet at
> start (a host reboot starts containers in no set order) is watched too: its
> service is left out until the name resolves, then the container restarts and
> configures it.

## 2. Reading the address from a program

Two ways, both stable:

**A. The mounted file (no hiddenforge installed):**

```
<keys>/<name>.onion          # e.g. ./tor-keys/myapp.onion, one line, mode 0644
```

hiddenforge publishes this once the service is actually reachable -- Tor holds
established introduction circuits for it AND has uploaded its descriptor to the
network -- not merely once Tor has written the key. Measured: without the upload
check the file appeared about 45 seconds before any client could reach the
address; with it, a fetch made the moment the service reported ready succeeded,
on a fresh key and after a restart. Any process
that can read the mount can read it. (The service directory itself is `0700`
owned by the container's `tor` user, so other files inside it are not readable by
your host user; `<name>.onion` is the readable copy.)

**B. `show --json`:**

```bash
hiddenforge show --keys ./tor-keys --name myapp --json
```
```json
{"address_path":"./tor-keys/myapp.onion",
 "key_path":"./tor-keys/myapp/hs_ed25519_secret_key",
 "name":"myapp",
 "onion":"abcdefghijklmnopqrstuvwxyz234567abcdefghijklmnopqrstuv.onion",
 "public_key_path":"./tor-keys/myapp/hs_ed25519_public_key",
 "source":"published",
 "derived_matches":null,
 "ok":true,"exit_code":0}
```

- `--name` → a single object with `onion`, `key_path`, `name` (plus extras).
- no `--name` → `{"addresses":[...],"address":"<first or null>"}`.
- exit code `4` means the address is not published yet; `onion` is `null`.
- `source` is `hostname` | `published` | `derived`: how the address was obtained,
  or `inconsistent` (exit `1`, no address) when `hostname` and the public key
  disagree; see Troubleshooting.
- `derived_matches` is `true` when the address was checked against the public
  key, `false` when they disagree, and `null` when the public key could not be
  read. From the host it is usually `null`: the key lives in the service
  directory, which belongs to the container's `tor` user.

The `key_path` is the **secret** key path; `show` never reads its contents.

## 3. Readiness: poll `ready`

```bash
hiddenforge status --container tor --keys ./tor-keys --json
```
```json
{"container":"tor","running":true,"healthy":true,"health_status":"healthy",
 "tor_bootstrapped":true,"vanguards":true,"hidden_service_published":true,
 "addresses":[{"name":"myapp","onion":"....onion"}],
 "address":"....onion","ready":true,"restarts":0,"dropped_mappings":[],"exit_code":0}
```

`dropped_mappings` lists any service or port mapping that was rejected and left
out of the torrc (a bad port, a malformed mapping, a name collision, or a backend
name that did not resolve yet -- that one is added automatically once it
resolves). It is empty when everything was accepted. Check it after any config change: a typo that
silently removed a service shows up here instead of disappearing.

Publish nothing until **`ready` is true**. It is `running` AND `healthy` AND
`hidden_service_published` AND every address present; bootstrap and Vanguards
count through `healthy`. The fields:

| field | meaning |
|---|---|
| `running` | the container is up |
| `healthy` | the healthcheck passes: bootstrapped, a circuit established, every service holding established introduction points with its descriptor uploaded to the network by this Tor, and Vanguards alive. Under Podman no engine healthcheck is set (rootless Podman 4.9 does not restart a container that has one when no systemd user session is reachable), so `health_status` is empty and `status` runs the same check itself |
| `tor_bootstrapped` | Tor reports `PROGRESS=100` |
| `hidden_service_published` | every configured service has a valid `hostname` (2.1.x under rootless Podman did not write the published `<name>.onion` file; 3.0 does) |
| `vanguards` | the guard-protection addon is alive |

`status --json` exits `0` when ready, `4` when not, and `2` if the container is not found. Inside the container the same
state is available granularly:

```bash
docker exec <container> su-exec tor python3 /usr/local/bin/healthcheck.py --json
```

## 4. Vanity addresses

```bash
# In the image, headless, writes ./tor-keys/<name>/{hostname,hs_ed25519_*}
hiddenforge vanity --prefix myapp --name myapp --keys ./tor-keys --threads 8 --json
```
```json
{"name":"myapp","onion":"myapp....onion","address_matches_prefix":true,
 "key_path":"./tor-keys/myapp/hs_ed25519_secret_key","key_dir":"./tor-keys/myapp",
 "threads":8,"ok":true,"exit_code":0}
```

- Prefix characters are base32: `a-z` and `2-7` (no `0`, `1`, `8`, `9`).
- Refuses to overwrite an existing identity without `--force`; with `--force` the
  old key directory is **archived** (`.replaced-<epoch>`), never deleted.
- Never prints or copies the secret key bytes.

**Estimate the cost first:**

```bash
hiddenforge vanity --prefix myapp --bench --seconds 5 --json
```
```json
{"keys_per_sec": 6200000.0, "threads": 8,
 "difficulty":[{"prefix_len":1,"average_attempts":32,"estimated_seconds":5.2e-06,"estimated_human":"<1s"},
               {"prefix_len":2,"average_attempts":1024,...}, ...]}
```

Expected attempts is exactly `32^length`; the time is that divided by the
measured throughput of *this machine*. At the 6.2 million keys/s above: 5 chars
takes seconds, 6 a few minutes, 7 about an hour and a half, 8 about two days;
on a machine ten times slower, multiply by ten.

**Long prefixes on a faster machine.** The generator is stateless: run the same
image on the fast box, then copy the key directory back.

```bash
# on the fast machine
docker run --rm -v "$PWD/keys:/keys" <image> vanity \
  --prefix myapp --name myapp --out /keys --threads 32 --uid "$(id -u)" --gid "$(id -g)"
# then, on the production host
rsync -a fastbox:keys/myapp ./tor-keys/myapp
chmod 700 ./tor-keys/myapp; chmod 600 ./tor-keys/myapp/hs_ed25519_secret_key
```

## 5. Key lifecycle

> The key **is** the address. Losing it loses the address permanently. There is no
> recovery and no reset. Encrypt your backups.

```bash
hiddenforge backup  --keys ./tor-keys --out ./keys.tar.gpg --tool gpg --passphrase-file ./pp --json
hiddenforge restore --keys ./tor-keys --input ./keys.tar.gpg --tool gpg --passphrase-file ./pp --json
hiddenforge rotate  --keys ./tor-keys --confirm ROTATE --json     # DESTRUCTIVE
```

- **Run `backup` with access to the service directories.** On a running
  deployment they belong to the container's tor user (0700), so from your own
  account the keys cannot be read. `backup` refuses rather than writing an
  archive without them -- it used to exit 0 over an archive holding only
  `<name>.onion`. Measured working: `sudo hiddenforge backup ...` under Docker,
  and `podman unshare hiddenforge backup ...` under rootless Podman. A volume
  with no key in it is refused too.
- `backup` picks the tool from the output file's extension (`.age`, `.gpg`) or
  `--tool`; otherwise `gpg` when there is no terminal (scriptable with
  `--passphrase-file`) and `age` on an interactive one. **`openssl` is refused**
  for creation (it has no authentication). gpg uses AEAD (OCB) when the local gpg
  supports it, else CFB with MDC unless `--require-aead` refuses that.
- `restore` refuses to overwrite existing files unless `--force`; with `--force`
  the replaced files are archived, not deleted.
- `rotate` refuses without the literal `--confirm ROTATE` and archives, never
  deletes, the old identity: a plain host directory is renamed to
  `tor-keys.rotated-<epoch>` and recreated empty; a key volume that is a mount
  point (always the case for `docker run <image> rotate`) keeps its place and its
  contents move into `tor-keys/.rotated-<epoch>/`. If any entry cannot be moved,
  nothing is. A running container keeps serving the old address until it is
  restarted.
- `encrypt-key` / `decrypt-key` wrap a single service key directory using the
  same tools. `decrypt-key` refuses to write into a directory that already holds
  a key set; with `--force` it moves that directory aside whole
  (`<name>.replaced-<epoch>`) and extracts into a fresh one. A key wrapped
  this way stays wrapped until `decrypt-key` restores it; the container cannot use
  it before then. To keep the key encrypted on the volume while the service runs,
  use `setup --encrypt-keys` instead (see the README).
- `restore`, `decrypt-key` and `vanity --force` remove the published
  `<name>.onion` for every key they replace: until the container republishes it
  from the new key, that file names the old address. `show` then reports "not
  ready" rather than a stale address.

> These four commands need `age` or `gpg` on the machine that runs them. The
> image intentionally ships no crypto tooling, so run them **on the host** (where
> your backup lives), not with `docker exec`. If no tool is present they fail
> closed with exit 2 and a clear `error` field.

All five accept `--json` and never prompt when stdin is not a TTY.

## 6. Verify the hardening of a running deployment

```bash
hiddenforge doctor --container tor --keys ./tor-keys --json
```
```json
{"ok":true,"failures":[],"warnings":[],
 "checks":[{"check":"cap_drop includes ALL","ok":true,"detail":"CapDrop=['ALL']","severity":"fail"}, ...]}
```

The capability, process-count and swap checks are MEASURED inside the running
container (PID 1's capability bounding set, the cgroup's `pids.max` and
`memory.swap.max`), not read from the engine's configuration: engines describe
the same setup differently, and podman-compose silently leaves some limits
unapplied. Where those files do not exist (cgroup v1) the engine's configuration
is used instead.

FAIL-level checks: `cap_drop` includes `ALL`; `cap_add` stays within
`{CHOWN,DAC_OVERRIDE,FOWNER,SETUID,SETGID}` and includes every capability the
runtime needs (all five under rootful Docker, `{CHOWN,SETUID,SETGID}` when the
engine reports rootless); `no-new-privileges`; read-only rootfs; seccomp NOT
unconfined; AppArmor applied (on hosts that have AppArmor); `pids_limit ≤ 512`;
swap disabled (`MemorySwap == Memory`); no published ports; the generated torrc
still contains every hardening directive (`ClientOnly`, `SafeLogging`,
`VanguardsLiteEnabled`, PoW, Intro-point DoS, ...); key dir `0700`; secret key
`0600`; and each key set's `hostname` agrees with its public key.
A container that is not restarted when it exits also FAILs: no engine restart
policy and no systemd unit running it. A systemd unit whose main process is the
container's conmon, with `Restart=always`, is a warning rather than a pass:
doctor cannot prove the unit recreates the container, and says how to check.
A log driver other than `none`, and `dns:` unset or not loopback, are warnings.
Exit `1` on any failure, `0` otherwise, `2` if the container cannot be inspected.

Inside the container (no docker socket):

```bash
docker exec <container> su-exec tor hiddenforge doctor --keys-only --json
```

## 7. Machine contract

```bash
hiddenforge info --json        # the full contract (same bytes as manifest.json)
hiddenforge version --json     # {"name","version","contract_version","ok","exit_code"}
```

`manifest.json` describes the image: env vars, ports (`[]`), volumes (with
`contains: ["keys","address"]`), tmpfs, health command + `ready_field`, the
address command and file paths, the key file formats/modes, and the exit codes.
Pin `contract_version`; it only changes if a field is removed or changes meaning.

### Verify the image, and generate an SBOM

```bash
hiddenforge verify-image sambent.dev/sam/hiddenforge:latest --json
```

Resolves the registry digest with `skopeo` (no pull), compares it to
`signatures/hiddenforge.digest`, and verifies both halves of the hybrid
signature over that digest: SSH-FIDO2 (YubiKey, via `ssh-keygen`) and ML-DSA-65
(post-quantum, via OpenSSL 3.5 or later, falling back to `pqsign` if OpenSSL is
older). The digest file is read once and the same bytes feed every check.

**The trust anchor is pinned in the CLI**, not read from the signature
directory: the release signer keys (`PINNED_ALLOWED_SIGNERS`) and the SHA-256 of
the ML-DSA public key (`PINNED_MLDSA_PUB_SHA256`). A signature directory whose
keys have been replaced fails, however valid the replaced signatures are. To
verify an image signed by someone else, name their keys explicitly with
`--allowed-signers FILE` and/or `--mldsa-pub FILE`; the result then says
`"trust_anchor": "operator-supplied"`.

A hybrid signature with one half unexamined is **not verified**: if the ML-DSA
signature is missing from the set, or neither OpenSSL 3.5+ nor `pqsign` is
available to check it, the command
fails (exit 1). `--allow-classical-only` accepts the SSH-FIDO2 signature alone,
and `--allow-pq-only` accepts the ML-DSA signature alone when the SSH-FIDO2 one
is missing (a release signed before the hardware key was available); either
way the result reports `complete: false`, and an image with neither signature
verified is refused even with both flags. `--skip-registry` verifies the
signatures without comparing the registry, and is likewise reported as
`complete: false`. Result fields: `registry_digest`, `signed_digest`,
`digest_match`, `ssh_fido2`, `mldsa`, `trust_anchor`, `failures`, `unchecked`,
`complete`. Exit `0` verified, `1` not verified, `2` bad arguments.

**A deploy gate should require `ok and complete`.** `ok` is false whenever a
check failed or a check the operator did not opt out of could not run; `complete`
is false whenever anything at all was left unchecked, including by an explicit
opt-out.

```bash
hiddenforge sbom --image sambent.dev/sam/hiddenforge:latest --out hf.spdx.json --json
```

Runs a digest-pinned `anchore/syft` over the image and writes a normalised SPDX
JSON document (`documentNamespace` and `creationInfo.created` are pinned so the
output is stable). Requires the docker engine (for its socket). Exit `0` written,
`1` syft failed or produced zero packages.

### Exit codes

| code | meaning |
|---|---|
| 0 | success |
| 1 | refused or failed (see stderr / the `error` field) |
| 2 | usage, validation, or environment error |
| 3 | a key appeared at the output path while a search was running |
| 4 | not ready yet (`status`: the container exists but is not ready, see `reason`; `show`: no address yet) |
| 130 | aborted at an interactive prompt (empty answer, end of input, or Ctrl-C) |

### Using the image directly (no host CLI)

Every key command is also a subcommand of the image, so `docker pull` is enough:

```bash
docker run --rm <image> version --json
docker run --rm <image> info --json
docker run --rm -v "$PWD/tor-keys:/keys" <image> vanity --prefix hi --name myapp \
  --out /keys --uid "$(id -u)" --gid "$(id -g)"
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/out:/out" <image> \
  setup --backend web:80 --name myapp -o /out
```

`--user` makes the generated files yours rather than root's (`setup` needs no
privilege). Paths it prints, such as the `merge` command, are the container's
(`/out/...`); on the host the files are in `./out`.

## 8. Consumer examples

**Shell**

```bash
#!/usr/bin/env bash
set -euo pipefail
mkdir -p ./tor-keys
docker compose -f compose.yml -f ./deploy/compose.service.yml up -d
until [ "$(hiddenforge status --container tor --keys ./tor-keys --json \
          | python3 -c 'import json,sys;print(json.load(sys.stdin)["ready"])')" = "True" ]; do
  sleep 5
done
onion=$(hiddenforge show --keys ./tor-keys --name myapp --json \
        | python3 -c 'import json,sys;print(json.load(sys.stdin)["onion"])')
echo "published at http://$onion"
```

**Python (stdlib only)**

```python
import json, subprocess, time

def ready(container="tor", keys="./tor-keys"):
    out = subprocess.check_output(
        ["hiddenforge", "status", "--container", container, "--keys", keys, "--json"])
    return json.loads(out)["ready"]

while not ready():
    time.sleep(5)

addr = json.loads(subprocess.check_output(
    ["hiddenforge", "show", "--keys", "./tor-keys", "--name", "myapp", "--json"]))
print(addr["onion"], addr["key_path"])
```

## 9. Troubleshooting

- **`show` exits 1 with `source: "inconsistent"`, `onion: null`**: the `hostname`
  file and the public key in that directory describe different addresses (a
  partial restore, or files from two services in one directory). Tor rewrites
  `hostname` from the key when it starts and serves the key's address, so no
  address is reported; both are in the document as `hostname_onion` and
  `derived_onion`, and `derived_matches` is `false`. Restore the whole directory
  from one backup. `derived_matches: null` means the comparison could not be made
  (no readable public key), which is not the same as agreement.
- **`show --json` exits 4 / `onion: null`**: the address is not available yet;
  the `error` field says which case. Either Tor has not generated the key (poll
  `status --json` until `ready`; first boot takes a few minutes, up to about 6), or the key exists
  but its directory is not readable from the host and the published
  `<name>.onion` has not been written yet. Under Docker that file appears once
  the service is reachable (under rootless Podman, 2.1.x never writes it; 3.0
  does). Until then, read the address inside the container (below).
- **`status` says `container not found`**: pass `--container <your-compose-service>`;
  hiddenforge resolves Compose service labels automatically.
- **The onion was reachable, then stopped after a redeploy**: the supervisor
  follows a backend that moved to a new IP by restarting the container, which
  needs a restart policy on it (the shipped files set one). Without one the
  container stops instead of forwarding to a dead address; bring it up again
  with your usual compose `up -d`.
- **`show` says the key volume cannot be enumerated**: that is intentional; the
  volume is `0751` (traverse, not list). Pass `--name <service>`.
- **rootless Podman**: use `podman-compose.yml`, and read the `.onion` with
  `podman-compose exec tor su-exec tor cat /var/lib/tor/hidden_service/<name>/hostname`
  (the `su-exec tor` is required; see the rootless notes in the README).
